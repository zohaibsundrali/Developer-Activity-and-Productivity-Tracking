# Application audit — 11 September 2026

This audit covers the Next.js web application in `website_project/tracking` and inspects the Python desktop tracker in `developer-tracker`. It is not a certification that every user journey or database policy is correct. Local fixes are not deployed. Connected database changes require SQL access that the Supabase connector denied.

## Findings and fixes

| Area | Root cause | Change | Verification |
|---|---|---|---|
| API authentication | Missing memberships, failed membership queries, and unknown statuses could retain JWT privileges; current role was not consulted | Require an active membership; use the lower privilege of current membership and Auth metadata during partial role changes | Behavioral regression tests for missing/inactive/pending membership, lookup errors, demotion, partial demotion |
| Database authentication | RLS helpers read JWT claims without checking current membership; suspension/removal did not immediately revoke direct database access | Prepared `audit_membership_authority` migration | Isolated PostgreSQL tests; not applied to connected project |
| Dashboard permissions | Effective permissions were lost on reload; sidebar and section checks used role defaults; late or failed lookups could retain previous grants | Reload permissions before mounting staff dashboards; use effective permissions for navigation; reject unavailable overrides and stale responses | Unit tests and browser reload/error/retry tests |
| Billing verification | Subscription/plan query errors were ignored and failed counts were treated as zero | Retryable failures refuse creation instead of granting access or falsely demanding an upgrade | Behavioral tests for returned errors, rejected queries, missing/invalid counts |
| Seat limits | DevOps was absent from seat mapping; HR/Finance used developer profile rows but checked only employee limits | Check both meters for every role stored in developers | Regression tests for all three roles |
| Invitation scope | Service-role writes accepted team, department, and project IDs without checking organization ownership | Validate optional references at creation and acceptance | Cross-tenant/missing-reference/query-failure tests |
| Invitation acceptance | Membership, project link, Auth linkage and final invitation update errors were discarded | Check each required write, compensate newly created rows/Auth account on failure, condition final consumption on pending/unexpired invitation | Failure-injection tests; no real invitations sent |
| Production ingest | Anonymous activity and screenshot writes were accepted by default | Require configured shared-secret authentication in production even if enforcement flag is false | Production endpoint regression tests |
| Production demo billing | Missing Stripe configuration automatically enabled free paid-plan activation | Require explicit `BILLING_DEMO_ENABLED=true` in production; public plan response agrees | Behavioral tests for default refusal and explicit demo mode |
| Unpaid subscriptions | Webhook rewrote an unpaid paid plan to Free, and Free never locks | Keep paid plan identity when unpaid so the workspace lock applies | Webhook-to-access-state regression; cancellation still reverts to Free |
| Notification privacy | Same-organization Owner/Admin could read other recipients' notifications directly | Prepared recipient-only SELECT/UPDATE policies, including restrictive policies over legacy grants | Live read-only reproduction; isolated PostgreSQL read/update/reassignment/client tests |
| Framework security | Next.js 14.0.0 predates security patches | Updated Next.js and matching lint configuration to 15.5.24 | Build, unit and browser regression runs |
| QA reliability | Two tests matched an exact import statement instead of its contents; full Admin walk exceeded a single-screen timeout | Accept shared role import with additional names; increase only whole-console journey budget | Full regression suite and repeated Admin walk |

## Connected database observations

The connected catalogue has **Free, Professional, Business, Enterprise**. No Basic plan exists. All twelve configured role accounts authenticated; their membership roles/types agreed with Auth metadata. Direct queries returned zero cross-organization projects for all twelve roles. A control browser test verified the other organization's project exists and its owner can open it.

Owner could read 15 notifications addressed to others; Admin could read 21. Other tested roles returned no foreign-recipient notifications. These are existing records read through each user's own token, not synthetic source assertions. The recipient policy correction remains pending deployment.

The project had 18 memberships, 4 projects, 18 tasks, 1 invitation, 38 notifications, **zero employee_profiles**, and **zero user_permissions** at inspection time. Empty tables limit realistic onboarding and per-user override testing; browser override tests use intercepted display responses and do not establish live RLS override correctness.

The six inspected storage buckets are private. Anonymous count probes returned zero visible rows for ten sensitive tables; two other table counts were unavailable and must not be interpreted as zero. A single admin row still has a non-null password value outside the application's hash format. No password value was fetched. Its `auth_user_id` is populated, but verification through the Auth admin API failed; guarded cleanup stopped before any update. That record needs account-link repair and credential-copy removal, with rotation if an actual credential was exposed. Developer and client password columns had zero non-null values.

## Remaining issues and limits

- **Database migrations are prepared, not deployed.** Supabase MCP SQL inspection returned “You do not have permission to perform this action.” Live policy definitions, grants, all triggers, migration history and advisors could not be inspected through that connection. Review and apply the two new migration files after database/096, then rerun database probes and the supplied regression queries in a staging database.
- **Plan enforcement is incomplete at the database boundary.** Existing migration 028 derives limits from `plan_code`, ignoring expiry, counts without serializing concurrent inserts, and runs only on INSERT. Seat checks in API code are not atomic with insertion. Reopening tasks and concurrent creations require transactional database enforcement. The source must not be considered bypass-proof.
- **Storage, screenshot and history ceilings are not comprehensively enforced.** `storage_mb` has no shared byte accounting; direct desktop writes bypass HTTP checks; history limits have no enforced query window/retention policy. No destructive retention policy was invented or run. `reports` is not enforced across all report paths; `api_access` describes no implemented public API. Existing UI source explicitly labels these gaps.
- **Permission overrides are only partly implemented in RLS.** Migration 094 rewrites a subset of capabilities; other role-list policies do not uniformly consult per-user overrides. Some operations bundle multiple field-level permissions into one table policy. The UI/API improvements do not prove every direct database mutation honors every catalogue key.
- **Shared-secret ingest is fleet-wide**, not bound to one developer/device. Anyone holding the secret can submit another developer's ID. Per-device enrollment/revocation remains needed for a complete device identity boundary.
- **Invitation/account creation spans multiple services.** Compensation now checks/logs cleanup failure, but network loss/process death can still leave partial records. A transaction-backed acceptance workflow plus reconciliation is needed for crash/concurrency guarantees. Terms acceptance remains best-effort according to the existing business behavior.
- **Notification recipient isolation is not event authorization.** Writers still require comprehensive checks that a recipient can access each referenced entity. Real email delivery, push/realtime subscription behavior across all events, and every deep link are not comprehensively verified. Client support/announcements use separate portal surfaces.
- **Real payment journeys remain unverified.** No Stripe secret/webhook configuration is present in the inspected application environment. Hosted checkout, payment failures, portal cancellation/resume, upgrades/downgrades and real webhook delivery require Stripe test credentials and configured price IDs.
- **Desktop runtime remains unverified on Windows.** Python syntax compilation passed. Readiness self-test reported 2 passes, 15 failures and 1 platform warning: dependencies/display/input capture are unavailable in this Linux environment. Installation and real keyboard/mouse/screenshot/session behavior need the target Windows environment.
- **Outbound messages and destructive seed flows were not executed.** Browser tests ran with `E2E_ALLOW_WRITES=0` and `E2E_SEED=0`. Skips must not be counted as passing write journeys. No production deployment or real charge was performed.
- **Dependency-wide vulnerability check remains pending approval.** Automatic approval review rejected `npm audit` because it transmits dependency metadata to npm. The public Next.js advisory was checked independently; the framework update used `--no-audit`. This is not a clean bill of health for all transitive packages.

## Deployment notes

- Deploy the application changes only after normal review. The application repository is `website_project/tracking`; its Git metadata was verified during PR preparation. The earlier check at the workspace root incorrectly reported that Git metadata was unavailable.
- Apply both new files under `supabase/migrations` **after** the existing SQL sequence through 096. These files do not bootstrap the historical schema. Test fixture SQL is for an isolated database only.
- Production HTTP desktop-ingest clients must send `DESKTOP_INGEST_SECRET`; unset configuration now fails closed.
- Leave `BILLING_DEMO_ENABLED=false` for real customers. `true` intentionally permits unpaid demo grants and must only be used for demo installations.
- Repair missing/inactive membership records through a legitimate account-management flow; the server no longer treats their absence as an active account.
